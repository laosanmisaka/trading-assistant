## 3. 优先级问题：4.1 缺席

### 3.1 先说清单对的部分

清单完全没提**做 T 资金/仓位不守恒**（`core/trading/t_trader.py`，见 `docs/PROJECT_ASSESSMENT.md` 4.1）。我这次复核了它的真实影响面：

```
grep -rn "TTrader|t_trader" ui/     →  零匹配
全项目引用仅：core/trading/simulator.py、tests/test_t_trading.py
```

**结论：`TTrader` 在 UI 层零引用，是"引擎有、界面没接"的半成品。所以它当前不会算错真钱。** 从这个角度看，清单不把它排进高优先级**可以理解**。

### 3.2 但漏掉而不说明，等于埋雷

正确做法不是"不修"，而是**明确标注它的前提条件**：

1. **它是"接线即事故"型的缺陷。** 实测 `BUY_FIRST` 路径每轮资金净减 10,000，而 `max_trades = n_lots = 5` —— **第 5 轮资金归零后 `open()` 静默返回 `None`，不报错、不记日志**。任何一天把做 T 界面接上去，它不会崩，只会悄悄停摆。
2. **它是项目唯一的策略验证通道。** `core/trading/simulator.py` 是回测/仿真入口（对应提交 `75a8157`「可插拔策略的回测引擎」）。**基于 `TTSimulator` 得出的任何做 T 策略结论，目前都不可信。**
3. **它是双向缺陷，不止清单未提的那一半。** `SELL_FIRST` 路径方向相反——每轮资金 **+10,000**（卖出所得从未入账，回补时却加回来），底仓同样漂移。

**建议：要么列入任务，要么在清单末尾加一条"已知未处理缺陷台账"，写明「做 T 引擎资金双向不守恒 / 未接线 / 接线前必须先修」。静默略过是最差的选项。**

### 3.3 4.2 与 4.3 的处置——三条缺陷性质并不相同

清单同样没有覆盖 `docs/PROJECT_ASSESSMENT.md` 的 4.2 与 4.3。但把三条放在一起谈是错的，它们的**存活状态完全不同**：

**另外必须修正上一版报告中的一处错误结论**（本次复核推翻）：

> 旧表述：「买入日早于 120 天前 → `buy_idx` 仍为 `-1` → 落到 `new_sl = current_daily_low`，止损被静默设成今日最低价」

这是**错的**。第 117-120 行用的是 `str(d)[:10] >= first_buy_date[:10]`（`>=`），所以买入日早于窗口时匹配到的第一根 K 线让 `buy_idx = 0`，**不会**是 `-1`。真实后果是止损被算成 `max(lows[0:])` = **最近 120 天内的最高 low**，遗漏 120 天以前的历史极值 → 长线持仓的**止损线偏低**（更宽松），而不是"设成今日最低价"。

`buy_idx == -1` 是另一条独立路径，只在所有日线日期都早于买入日时发生（典型是当日买入但日线未更新），该分支结果恰好合理。**两条路径的共同问题是都没有回退告警**，使用者无法察觉止损基于不完整的窗口。此修正已同步至 `docs/PROJECT_ASSESSMENT.md` 4.3 第 3 点。

## 4. 技术方案上的两处风险

### 4.1 任务 3 的「模块级共享连接」有线程安全隐患

清单写「SQLite WAL 模式（支持并发读）」。**WAL 支持并发读是对的，但 `sqlite3.Connection` 对象本身不是线程安全的**——默认 `check_same_thread=True` 下跨线程使用会直接抛 `ProgrammingError`。

这个项目有多个 QThread Worker（`StockSearchWorker`、`IncrementalRefreshWorker`、`BuyPointScanWorker`），它们都会访问 DB。所以「共享连接」方案只有两条路，都不是免费的：

- `check_same_thread=False` + 自己加锁 → 把并发读变回串行，收益被抵消；
- 按线程隔离连接（`threading.local`）→ 复杂度上升。

**建议调整执行顺序：先做「减少连接次数」这类零风险的部分**——合并 `get_manual_alert` 的重复调用、`_update_profit_status`（`main_window.py:456` / 循环内 `:470`）改聚合 SQL——**再评估连接复用**。直接照单执行共享连接会引入新的偶发故障，而且很难复现。

### 4.2 任务 8 的表述不准确，危害被夸大

清单说「`data_ready` 和 `finished` 都连到同一收尾函数，每轮执行两次」。

实测（`main_window.py:376/378/410/421`）：

```python
self._inc_worker.data_ready.connect(self._on_incremental_complete)        # 376
self._inc_worker.finished.connect(self._on_incremental_complete_safe)     # 378
```

连的是**两个不同的槽**，只是都汇聚到 `_on_incremental_finished`（410 行）。而且第 421 行有 `if quotes:` 守卫——第二次带 `{}` 的调用**不会**用空数据覆盖行情或告警，只是重复设了一次状态栏文字。

**所以这是"设计脆弱点"，不是"当前 bug"。** 清单把它放在低优先级是**恰当的**；但理由需要改：真正要防的是"将来有人去掉那个 `if quotes:` 守卫"，而不是现在正在发生两次收尾。

另：真正的时序隐患在于 `finished` 与 `data_ready` 的**到达顺序不保证**，当前靠 `if quotes:` 兜住了。修的时候顺手把这个意图写成注释或断言，比单纯去重更有价值。

### 4.3 任务 9 的实际情况比你写的更严重一层

你说「底分型确认取 `lows[idx+1]` 而非分型本身最低价」。我核对后发现**代码与它自己的注释也不自洽**：

- `core/technical.py:150-172` `detect_bottom_fractal()` 返回的索引，按 docstring（155-156 行）明确是「**分型最低价实际所在的原始K线**」，即**中间K线**。旁证：同文件 `:183` 的 `get_latest_top_fractal` 直接用 `highs[idx]` 当顶分型价——说明「idx = 分型本身」是作者的既有约定。
- `core/buy_point_scanner.py:111-114` 注释写「确认: **第三K线收盘 > 底分型最低价**」，代码却是：

```python
bottom_low   = w_arr["lows"][idx + 1]    # 右K线的最低
confirm_close = w_arr["closes"][idx + 2] # 第四K线的收盘
```

按 `idx` = 中间K线的语义，注释意图应写作 `lows[idx]` 与 `closes[idx+1]`。**代码整体后移了一根**，实际校验的是「第四K线收盘 > 第三K线最低价」——这既不是注释描述的规则，也不是任何标准缠论确认规则。

**清单「勿直接改、需确认口径」的处置是对的，建议在描述里补上「注释与代码不一致」这一层**，因为它是比"取值选择"更硬的证据。
